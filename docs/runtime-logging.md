# 実行ログ

`pnpm baseline`と`pnpm fork`によるシミュレーションは、実行ごとに`out/logs/<run-id>/`へ診断情報を保存します。通常の世界の実行結果は、これまで通り`out/runs/<run-id>.json`です。比較実験の介入条件は`out/experiments/`に置きます。単発のモデル評価スクリプトはこの実行ログの対象外です。

## 見守るとき

端末には開始、ログの場所、各日の完了、終了だけを表示します。APIの試行や成功件数は流しません。再試行を経て完了した場合は、終了行にその旨だけを添えます。`--verbose`を付けると、各日の物語イベントと終了時の支持者一覧も表示します。

まず開始時に表示された`status.json`を読みます。これは詳細ログを読み続けずに状況を把握するための小さなファイルです。

```sh
cat out/logs/<run-id>/status.json
```

主な項目は次の通りです。

| 項目 | 意味 |
| --- | --- |
| `status` | `running`、`completed`、`failed`、`interrupted` |
| `targetDay` / `completedDay` | 指定した終了日 / 保存済みの日末状態の日付 |
| `phase` | 最新の処理段階と日・ターン・開始時刻 |
| `activeRequests` / `oldestRequest` | 未完了の問い合わせ数 / 最も古い問い合わせのID・開始時刻・試行番号 |
| `updatedAt` | 状況ファイルの更新時刻。実行中は約1秒ごとに更新 |
| `lastActivityAt` | 処理段階や問い合わせなど、最後にイベントが発生した時刻 |
| `models` / `errors` | モデル別の成功・失敗・再試行・キャッシュ・トークン集計 / 試行失敗の種類別集計 |
| `failure` | 実行が失敗・中断した原因のメタデータ |
| `pid` | 実行プロセスのID |
| `resultFile` | 正常終了した世界の保存先 |

`updatedAt`の更新は、モデルの応答が進んだことまでは意味しません。待ち時間は`phase.startedAt`、`oldestRequest.startedAt`、`lastActivityAt`と合わせて見ます。再試行数は初回以降に実際に開始した試行数です。キャッシュへのアクセスや同一の進行中問い合わせの共有は、API呼び出しとは別に数えます。

`completed`は指定した終了日まで正常に実行できたことを表します。`--until 2`なら2日目までの完了であり、物語全体の完了ではありません。

## 必要なときだけ詳細を読む

`events.jsonl`は1行1イベントの追記ログです。実行・各処理段階の開始と完了、問い合わせと各試行の開始、失敗、復帰、キャッシュ利用を記録します。問い合わせには`requestId`を付け、開始時の日・ターン・処理段階を終了まで保持します。所要時間はミリ秒です。

例えば、Jevで再試行が増えた場合は失敗した試行だけを絞ります（以下は`jq`を使う例です）。

```sh
jq -c 'select(.type == "attempt.failed") | {at, requestId, model, phase, attempt, error}' out/logs/<run-id>/events.jsonl
jq -c 'select(.requestId == "対象のID")' out/logs/<run-id>/events.jsonl
```

エラーは名前・HTTPステータス・エラーコード・再試行可否・原因の連鎖を記録します。`category`はメッセージから判定した補助分類です。生のエラーメッセージ、レスポンス本文、認証ヘッダー、プロンプトは診断ログにコピーしません。メッセージだけで区別できる提供元の詳細は残らないため、`other`を具体的な原因と決めつけないでください。モデルの回答や物語は既存の世界JSON・モデルキャッシュで確認します。

Jevの再試行待ち時間は`request.retry.delayMs`に残します。LLMはSDKの再試行をそのまま使い、ミドルウェアで各試行を観測します。LLMの再試行間隔はイベント時刻の差から確認できます。

## 失敗・中断時の保存

| ファイル | 内容 |
| --- | --- |
| `checkpoint.json` | 初期状態、または最後に完了した日末の世界。各日末に置き換える |
| `partial-world.json` | 失敗・中断時の世界。処理途中の変更を含みうる診断用データ |
| `status.json` / `events.jsonl` | 失敗した段階、原因、そこまでの問い合わせ履歴 |

JSONファイルは一時ファイルを書いてから置き換えます。失敗・中断した世界を`out/runs/`の正常終了結果として公開しません。`checkpoint.json`は自動再開機能ではありません。最終日の後継者指名は日末処理の後なので、その結果は正常終了時の世界JSONで確認します。

通常の例外は`failed`、CLIでのSIGINT（Ctrl+C）・SIGTERMは`interrupted`として記録します。SIGKILL、電源断、保存先の障害では最後の状態を書けないことがあります。`running`のまま更新が止まった場合は、時刻とプロセスの生存も確認してください。

並列問い合わせの一つが失敗した後も、既に送信した他の問い合わせが完了することがあります。その記録は追記しますが、実行の`failed`状態を正常終了へ戻すことはありません。実行結果の巻き戻しや自動再開、リクエストのタイムアウト変更は今回のログ機能には含めていません。
